PROPOSITO
================================================================================

Este documento resume la estructura real de la base de datos actual para crear
una V2 completamente versionada por migraciones.

Problema central:
La base actual no nace completa desde migraciones. Una parte esta versionada en
database/migrations y otra parte fue creada manualmente o importada desde dumps.
La V2 debe convertir TODO el esquema real en migraciones Laravel ordenadas,
revisables y reproducibles.

Uso recomendado junto a los 3 TXT:
1. prompt-reconstruccion-crm-v2.txt: vision, reglas y proceso.
2. contexto-codigo-crm-v2.txt: mapa del codigo Laravel actual.
3. contexto-db-crm-v2.txt: mapa de DB real, tablas legacy y migraciones faltantes.

================================================================================
REGLA PRINCIPAL PARA LA V2
================================================================================

La V2 debe poder levantarse desde cero con:

composer install
php artisan migrate --seed
npm install / npm ci
npm run build

Eso significa:
- Toda tabla debe tener migracion create_* o alter_*.
- Toda vista debe tener migracion.
- Todo stored procedure debe tener migracion.
- Todo trigger debe tener migracion.
- Todo indice importante debe tener migracion.
- Todo catalogo base debe tener seeder/factory si aplica.

No se debe depender de dumps SQL productivos para construir la estructura.

================================================================================
DECISIONES DE DISENO DB PARA LA V2
================================================================================

1. Migraciones baseline:
Crear migraciones desde cero para todo el esquema V2. No copiar dumps como fuente
final.

2. Naming:
Normalizar snake_case minuscula. Preservar columnas legacy solo si son necesarias
para ETL o compatibilidad temporal.

3. PK:
Todas las tablas con id bigint unsigned auto_increment, salvo pivots justificadas.

4. FKs:
Agregar FKs reales en tablas operativas. En historicas masivas, evaluar caso por
caso por performance y por naturaleza inmutable.

5. Bet/Net:
No unificar automaticamente. Evaluar:
- columnas
- volumen
- queries
- reportes
- diferencias de negocio
- costo de indices y particiones

6. Historicas:
Para ventas/premios/recargas/pagos/asistencias:
- evaluar particionamiento por fecha
- indices compuestos por query real
- tablas resumen diarias/mensuales
- ETL por chunks

7. BI:
Usar modelo operacional normalizado + tablas resumen/materializadas para reportes
pesados. No forzar 3FN en cada consulta historica si rompe performance.

8. Vistas/SP/triggers:
Versionar cada uno. Si un stored procedure es logica de negocio mantenible en PHP,
considerar moverlo a Service + Job.

ETL RECOMENDADO
================================================================================

Tablas de control:
- etl_runs
- etl_run_items
- etl_conflictos
- legacy_id_maps

Cada comando ETL debe:
- leer de DB legacy por chunks
- transformar nombres/tipos/catalogos
- hacer upsert idempotente
- registrar errores por fila sin tumbar todo el proceso
- validar conteos
- validar sumas para columnas de monto
- poder reanudarse

Validaciones minimas por tabla historica:
- COUNT(*)
- SUM(monto)
- MIN(fecha)
- MAX(fecha)
- conteo por sistema
- conteo por mes
- conteo de nulos en campos clave

No ejecutar ETL destructivo sin aprobacion.
